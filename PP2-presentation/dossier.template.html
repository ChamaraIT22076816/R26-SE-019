01The headline, stated correctly

The evaluation set is imbalanced 524 : 992. Raw accuracy flatters under that, so it is never quoted alone.

A model that always answered “different sign” would score 65.4%. The scorer’s best single threshold reaches 74.6% — a gain of 9.2 points, not 74.6 from nothing. The threshold-free reading, which the imbalance cannot distort, is an ROC AUC of 0.744.

If asked “why only 74%?”

“It’s 74.6% against a majority baseline of 65.4%, so the gain is 9.2 points — and I’d rather state it that way. But the more important point is that this figure characterises the distance metric, not the product. The module never applies a threshold.”

Do not conflate

This is not the proposal’s ≥90%-accuracy-against-expert target. That one measures grading against an SSL teacher’s judgement and is not yet measured — it needs learner attempts a teacher has graded.

02Score-scale calibration

The corpus labels itself, so the score scale is fitted to measured data rather than guessed.

Two takes of one sign by the same signer are a correct rendition performed twice; takes of different signs are a wrong-sign attempt. No human annotation is involved and none is claimed.

The score anchors D_PERFECT = 0.22 and D_ZERO = 0.77 are the p10 and p90 of the measured correct-rendition distribution. The best tenth of correct renditions score 100; the worst tenth score 0.

If asked what calibration changed

“Before calibration a genuinely correct attempt could score zero, because the anchors were guessed and one of them sat below the median correct rendition. Fitting them to the data fixed a real bug, not a cosmetic one.”

03What the learner actually sees

The shipped system applies no threshold. It maps distance to a continuous 0–100 score.

This is the operationally meaningful result. The threshold accuracy in §01 describes a classifier the product does not contain; this describes the signal a learner receives.

04Fitting the feature weights — and declining the maximum

A grid search found a better score than the one that shipped. It was rejected on purpose.

The search optimises “is this the same sign?” — a classification objective. This scorer grades a known sign. Movement is a phonological parameter of SSL, so a scorer blind to it would award full marks to a learner with the correct handshape and the wrong movement.

If asked for a design decision

“Our grid search found 78.6% and we shipped 74.2%. The maximum is at zero movement weight, and movement carries linguistic meaning in SSL. We took the measured gain up to 0.8 and stopped, because optimising the available metric instead of the actual goal is the mistake we were trying not to make.”

05A grader, not a classifier

Measured evidence for the distinction the whole design rests on.

A high score is therefore not proof the right sign was made. This is why the scenario rubric’s appropriateness component compares only within a scenario’s small vocabulary rather than across all 490 references — a bounded closed-set judgement is meaningful where an open-set one would not be.

06Per-sign behaviour

One global threshold does not fit every sign, and the chart is how that became visible.

THANK_YOU is a clear outlier worth understanding rather than averaging away. It indicates either that a per-sign threshold is needed, or that this sign’s reference recording is poor. Both are actionable.

The operational definition excludes the camera’s sensor→browser delay and the display’s response time, because JavaScript cannot observe them — so every figure is a software pipeline latency, never glass-to-glass. It errs high in two places, which is the safe direction for an “under 300 ms” claim.

Never say

“Our feedback latency is 1.8 milliseconds.” It is the scoring stage. The end-to-end instrument exists and reports in the Progress tab, but it needs ~20 real attempts before its 95th percentile means more than “the second slowest one”.

09Targets and limitations

One of four measured, one with a stated proxy, two waiting on the pilot.

Proposal targetStatusWhat exists
≤ 300 ms feedback latencyMeasured1.8 ms median for the scoring stage; live end-to-end instrument built and reporting
≥ 90% accuracy vs expertProxy onlyAUC 0.744 / +9.2 over baseline. Needs learner attempts graded by an SSL teacher
≥ 20% learning gainPending pilotAttempts carry a session id, so “after N sessions” is countable
SUS ≥ 70Pending pilotNeeds the pilot and a questionnaire that does not yet exist

Limitations, stated rather than waited for:

  • One signer in the calibration corpus. The measured spread is the natural variation of one fluent person — narrower than a learner’s. Every constant fitted from it is therefore optimistic.
  • No Deaf validation of the references. The corpora are public and performed by real signers, but nothing has been reviewed by a Deaf signer for this project.
  • Non-manual markers are not scored. The build tracks hands only, so facial expression, head tilt and body movement are not captured. Their 10% is reallocated to accuracy — reporting a number for them would be fabricating one.
  • Appropriateness is a closed-set judgement. It detects confusion only with signs the library holds, and sharpens as the library grows.
  • Continuous, co-articulated signing is not evaluated. Phrases are scored sign-by-sign plus a phrase-level fluency metric.
  • Zero pilot participants to date.

10Reproduce it live

Three commands, about twenty seconds. Worth offering to run in front of the panel.

# 1 — run the suite; this regenerates the committed reports npm --prefix learn-ssl-module/web test
# 2 — export the raw measurements behind every figure cd learn-ssl-module/web; $env:EVAL_EXPORT=1; npx vitest run evaluation.export
# 3 — render the figures learn-ssl-module/tools/venv/Scripts/python.exe PP2-presentation/make_figures.py

After step 1, git diff -- '*-report.md' comes back empty — every regenerated report is byte-identical to the committed one.

On repeatability

“The reports are written by the tests that measure them and are marked ‘do not edit by hand’. We re-ran the whole suite last night and the committed numbers didn’t move by a character. The charts are plotted from a JSON export produced by the same scoring function the deployed app calls — the plotting script does no measurement of its own.”

Know this before you offer

The 557 calibration takes are derived data and are gitignored. Without them the calibration tests describe.skip — they go silently green rather than red. A passing suite on a fresh clone does not prove the calibration ran; check the corpus count printed in calibration-report.md.
