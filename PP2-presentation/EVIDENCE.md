## 4. Reproducing everything

Three commands, in order. Roughly 20 seconds total.

**1. Run the suite. This regenerates the committed reports.**

```bash
npm --prefix learn-ssl-module/web test
```

Then check the reports came out identical — this is the repeatability
demonstration, and it is worth running live:

```bash
git diff --stat -- 'learn-ssl-module/web/*-report.md'
```

Empty output means every regenerated report matched the committed one byte for
byte. Diffing the reports specifically, rather than reading whole-tree
`git status`, keeps the check meaningful while other work is in progress.

**2. Export the raw measurements.**

```bash
cd learn-ssl-module/web; $env:EVAL_EXPORT=1; npx vitest run evaluation.export
```

**3. Render the figures.**

```bash
learn-ssl-module/tools/venv/Scripts/python.exe PP2-presentation/make_figures.py
```

**Re-measure the committed latency report** (only on an idle machine, and only
when you intend to change a published figure):

```bash
cd learn-ssl-module/web; $env:BENCH_WRITE=1; npx vitest run scoring.bench
```

## 5. Two caveats to know before demonstrating this

**The calibration corpus is gitignored.** The 557 takes are derived data, 15 MB.
On a machine without them, `calibration.test.ts` and `weights.fit.test.ts` use
`describe.skip` — they go **silently green rather than red**. A passing suite on
a fresh clone therefore does *not* prove the calibration ran. Verify the corpus
count printed in `calibration-report.md`.

Restore from the archive outside git:
`OneDrive/…/Dataset/learn-calibration-takes.zip` (3.4 MB, 557 entries) →
unzip into `learn-ssl-module/web/calibration/`.

The committed reports preserve the numbers either way, so the published figures
do not depend on the corpus surviving — only the ability to re-derive them does.

**`npm run dev` regenerates the reference index via a `predev` hook.** Running
`npx vite` directly skips it and the app loads with no references at all.

The generated reports are correct in every case; the prose is what drifted. That

### One generated report *is* stale: `latency-report.md`

It describes **"40 references sampled evenly from the 362 on disk"**. There are
now **501**. It also lacks the `Measured **YYYY-MM-DD**` line that the current
`scoring.bench.test.ts` writes (line 212) — so the committed file was produced
by an earlier version of the bench, before both the corpus growth and the
date-stamping change.

**The figures themselves are still sound** — they measure the cost of the
algorithm, which depends on sequence lengths rather than on how many references
exist. Only the sample description is out of date.

**Recommended: refresh it.** A dated, corpus-accurate report is materially
better in front of a panel than one that misdescribes its own sample. Close
other applications first — the file regenerates only under an explicit flag
precisely because tail timing is sensitive to CPU load:

```bash
cd learn-ssl-module/web; $env:BENCH_WRITE=1; npx vitest run scoring.bench
```

**Expect the p95 to fall** (an incidental re-run tonight gave 3.8 ms against the
committed 12.6 ms). The median is stable at ~1.8 ms. If you refresh it, update
the figure in `EVALUATION.md` §8 to match, and re-check `README.md`. If you do
not refresh it, quote the committed figures and say the library has grown since
— either is defensible; quoting a p95 from one run and a sample description from
another is not.
